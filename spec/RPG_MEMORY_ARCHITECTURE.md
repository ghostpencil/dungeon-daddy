# RPG + Memory Architecture

## Core architectural rule

The RPG engine and memory layer are authoritative. The LLM is advisory.

The LLM may suggest narration, consequences, scene text, NPC voice, or memory summaries. It must not be the sole writer of mechanical truth.

Authoritative state belongs to:

- RPG service models
- DuckDB tables
- Markdown files with structured front matter
- domain events written by deterministic service code

## Existing architecture alignment

The repo currently separates:

- `views/` for Arcade views
- `ui/` for panels and widgets
- `map/` for renderers
- `llm/` for provider and agents
- `data/` for models and repository

The RPG and memory systems should extend this pattern rather than being placed inside `PlayView` or `DungeonMasterAgent`.

`PlayView` should orchestrate UI events and display state. It should not own RPG rules or memory write logic.

`DungeonMasterAgent` should receive context generated by a dedicated context bundle service. It should not query DuckDB directly.

## Proposed dependency direction

```text
views/play_view.py
  -> rpg/service.py
  -> memory/context_bundle.py
  -> llm/agents/dm_agent.py

rpg/service.py
  -> rpg/actions.py
  -> rpg/clocks.py
  -> rpg/stress.py
  -> rpg/fallout.py
  -> memory/repository.py only through explicit event/memory projection boundary

memory/context_bundle.py
  -> memory/retrieval.py
  -> memory/repository.py
  -> memory/markdown_store.py
```

Avoid reverse dependencies:

- `rpg/` must not import `views/` or `ui/`.
- `memory/` must not import `views/` or `ui/`.
- `llm/agents/` must not import `rpg/service.py` directly.
- `ui/panels/` must not modify DuckDB directly.

## Runtime flow

```text
User clicks action / sends command
  -> PlayView sends intent to RPGService
  -> RPGService resolves roll or state change
  -> RPGService emits domain events
  -> MemoryProjectionService creates/updates memory records when needed
  -> PlayView refreshes character sheet, clocks, chat, and memory indicators
  -> ContextBundleService builds context for DM narration
  -> DungeonMasterAgent drafts narration using the bundle
  -> User/GM sees result
```

## Domain event boundary

Use domain events to decouple systems.

Example event types:

- `scene.started`
- `scene.ended`
- `action.resolved`
- `stress.marked`
- `clock.advanced`
- `fallout.triggered`
- `fallout.resolved`
- `memory.created`
- `memory.updated`
- `dungeon.influence_changed`

The event log supports:

- debugging
- replay
- projection repair
- regression tests
- later analytics

## New module responsibilities

### `dungeon_daddy/rpg/models.py`

Defines the data structures for:

- `ActorState`
- `ActionRating`
- `StressTrack`
- `ClockState`
- `Ability`
- `ActionRequest`
- `ActionResolution`
- `FalloutRecord`

### `dungeon_daddy/rpg/dice.py`

Responsible for dice rolling only.

Must support deterministic tests by allowing seeded RNG or injected roll values.

### `dungeon_daddy/rpg/actions.py`

Responsible for Charge-style action roll calculation:

- dice pool construction
- highest die selection
- outcome classification
- momentum spend/gain
- consequence shell creation

### `dungeon_daddy/rpg/clocks.py`

Responsible for clock operations:

- create clock
- advance clock
- complete clock
- validate bounds

### `dungeon_daddy/rpg/stress.py`

Responsible for:

- stress track changes
- overflow detection
- recovery rules
- determining whether fallout evaluation is required

### `dungeon_daddy/rpg/fallout.py`

Responsible for:

- evaluating fallout severity
- selecting or constructing fallout records
- applying mechanical hooks
- creating dungeon influence side effects

### `dungeon_daddy/rpg/service.py`

Application-facing orchestration layer.

This is what `PlayView` should call.

### `dungeon_daddy/memory/repository.py`

DuckDB data access layer.

No UI logic. No LLM calls.

### `dungeon_daddy/memory/markdown_store.py`

Reads and writes Markdown memory files with YAML front matter.

### `dungeon_daddy/memory/retrieval.py`

Deterministic memory search and ranking.

Inputs include actor IDs, location IDs, tags, active fallout, open threads, and current scene.

### `dungeon_daddy/memory/context_bundle.py`

Builds LLM-ready context bundles.

The bundle must include provenance explaining why each memory was selected.

## UI boundaries

UI panels are consumers of service state.

They may emit user intents such as:

- resolve an action
- apply recovery
- create a clock
- add a note
- open memory inspector
- approve generated memory summary

They must not directly write tables or Markdown.

## Threading note

The existing app uses background threads for LLM calls. Keep deterministic RPG and memory operations synchronous unless they become slow.

LLM calls remain background-threaded.

DuckDB writes should be centralized behind one repository/service boundary to avoid accidental multi-writer behavior.
